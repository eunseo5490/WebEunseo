1. 논리 데이터 저장소 확인
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[ 모델링 절차 ]
개념 모델링 → 논리 모델링 → 물리 모델링

[ 주요 용어 ]
- 엔티티   : 데이터로 관리할 대상 (예: 회원, 주문)
- 속성     : 엔티티가 가지는 데이터 항목 (예: 이름, 나이)
- 관계     : 엔티티 간의 연관성
- 도메인   : 하나의 속성이 가질 수 있는 원자값들의 집합
             (예: '성별' 속성의 도메인 → '남', '여')
- 튜플     : 릴레이션의 행(Row). 튜플의 수 = 카디널리티

─────────────────────────────────────────────────────────────
■ 무결성 제약조건
─────────────────────────────────────────────────────────────

무결성 제약조건 : 릴레이션이 가질 수 있는 유효한 데이터 값의 범위를 제약하는 규칙

① 개체 무결성
   - 기본키(PK)에는 NULL이 들어갈 수 없고, 중복값도 허용하지 않는다.

② 참조 무결성
   - 외래키(FK) 값은 참조하는 테이블의 기본키 값과 동일하거나 NULL이어야 한다.

③ 도메인 무결성
   - 특정 속성 값은 반드시 그 속성에 정의된 도메인 범위 안의 값이어야 한다.
   - 구현 방법 : CHECK 제약조건, NOT NULL, 적절한 타입/길이 지정

─────────────────────────────────────────────────────────────
■ 함수적 종속성
─────────────────────────────────────────────────────────────

함수적 종속 : 속성 X의 값이 결정되면 속성 Y의 값도 하나로 결정될 때,
              "Y는 X에 함수적 종속되어 있다"고 한다. (X → Y)

종류
- 완전 함수 종속  : 기본키 전체에 종속 (복합키일 때 일부가 아닌 전체에 종속)
- 부분 함수 종속  : 복합키의 일부에만 종속 → 2NF에서 제거
- 이행 함수 종속  : A→B, B→C 일 때 A→C가 성립 → 3NF에서 제거
- 다치 종속       : 한 속성이 독립적인 여러 값을 가짐 → 4NF에서 제거
- 조인 종속       : 분해된 테이블을 JOIN했을 때 원본과 동일해야 함 → 5NF에서 제거

─────────────────────────────────────────────────────────────
■ 정규화 (Normalization)
─────────────────────────────────────────────────────────────

목적 : 함수적 종속성을 해소하여 이상 현상(Anomaly)을 제거

이상 현상 3가지
- 삽입 이상 : 데이터 추가 시 불필요한 데이터도 함께 추가해야 하는 현상
- 삭제 이상 : 데이터 삭제 시 필요한 데이터까지 함께 삭제되는 현상
- 갱신 이상 : 일부 데이터만 수정될 경우 데이터 불일치가 발생하는 현상

정규화 단계
- 1NF : 모든 속성 값이 원자값(더 이상 쪼갤 수 없는 값)이어야 한다.
- 2NF : 1NF 만족 + 기본키가 아닌 모든 속성이 기본키에 완전 함수 종속되어야 한다.
        (복합키의 일부에만 종속되는 부분 함수 종속 제거)
- 3NF : 2NF 만족 + 기본키가 아닌 속성들 사이의 이행 함수 종속을 제거한다.
- 4NF : 3NF 만족 + 다치 종속 제거
- 5NF : 4NF 만족 + 조인 종속 제거

2NF를 만족하지 못할 때의 문제
→ 기본키가 복합키일 때, 일반 속성이 복합키 전체가 아닌 일부에만 종속되는
  '부분 함수 종속'이 발생하여 삽입/삭제/수정 시 이상 현상이 발생한다.

정규화가 조회 성능을 떨어뜨리는 이유
→ 하나의 테이블이 여러 테이블로 분리되므로, 원하는 데이터 조회 시
  JOIN 연산 빈도가 증가하여 CPU와 디스크 I/O 자원을 많이 소모한다.

─────────────────────────────────────────────────────────────
■ 릴레이션 스키마 변환 규칙 (Mapping Rule)
─────────────────────────────────────────────────────────────

엔티티   → 테이블
속성     → 컬럼
UID      → 기본키(PK)
관계     → 외래키(FK)

1:N 관계의 FK 위치 규칙
→ 외래키는 항상 N쪽(자식 테이블)에 생성한다.
  1쪽 테이블의 PK를 N쪽 테이블에 FK로 추가하여 두 테이블을 연결한다.

─────────────────────────────────────────────────────────────
■ 논리 데이터 모델 검증
─────────────────────────────────────────────────────────────

- 필요한 데이터가 빠지지 않았는지 (입력/출력/연계 데이터 확인)
- 기존 시스템의 데이터 구조를 제대로 파악했는지 (기존 DB, 백업, 공통코드)
- 사용자 요구사항이 반영되었는지 (저장 용량, 백업, 보안, 데이터 전환)
- 데이터 흐름이 명확한지 (생성/조회/수정/삭제 흐름)
- 엔티티, 속성, 관계, 중복, 무결성 점검
- 접근 권한과 통제가 명확한지

■ 컬럼 타입 정의
─────────────────────────────────────────────────────────────

ORACLE
- 문자열 : CHAR, VARCHAR2(길이)
- 숫자   : NUMBER(자리수, 소수점)
- 날짜   : DATE

MYSQL
- 문자열 : VARCHAR(길이)
- 숫자   : INT, DECIMAL
- 날짜   : DATE, DATETIME

컬럼명 작성 규칙
- SQL 예약어 사용 금지
- 가능한 짧고 표준화된 명칭 사용
- FK로 설정된 컬럼명은 보통 참조하는 PK의 이름을 그대로 사용
  (의미가 다를 경우 변경 가능)

─────────────────────────────────────────────────────────────
■ 반정규화 (Denormalization)
─────────────────────────────────────────────────────────────

정의 : 조회 성능 향상을 위해 정규화된 데이터 모델을 의도적으로 중복/통합/분리하는 기법

단점 : 동일 데이터가 여러 테이블에 중복 저장되므로
       수정 시 모든 중복 위치를 찾아 수정해야 하며,
       누락 시 데이터 불일치(무결성 파괴) 및 이상 현상이 발생한다.

반정규화 유형

① 중복 테이블 추가
   - 집계 테이블 추가 : 합계/평균 등의 연산 결과를 미리 계산하여 별도 테이블에 저장
   - 진행 테이블 추가 : 현재 진행 중인 상태나 최신 트랜잭션 데이터만 별도 분리하여 관리
                        (예: 주문→결제→배송 중 현재 상태만 저장)
   - 특정 컬럼만 포함하는 테이블 추가

② 테이블 조합
   - 항상 함께 사용되는 두 개 이상의 테이블을 하나로 합치는 것

③ 테이블 분할
   - 수직 분할 : 컬럼별 사용 빈도 차이가 클 때, 자주 쓰는 컬럼과 그렇지 않은 컬럼을 분리
   - 수평 분할 : 특정 범위별 사용 빈도 차이가 클 때, 해당 범위별로 행을 분리

④ 테이블 제거
   - 반정규화로 인해 더 이상 사용되지 않는 테이블 삭제

⑤ 컬럼 중복
   - 다른 테이블에 있는 컬럼을 현재 테이블에도 추가로 저장

─────────────────────────────────────────────────────────────
■ 공간 효율성 vs 접근 속도 트레이드오프
─────────────────────────────────────────────────────────────

접근 속도 ↑ → 인덱스 추가, 반정규화(중복 저장) → 물리 공간 소모 증가, 공간 효율 ↓
공간 효율 ↑ → 극단적 정규화 → JOIN 빈도 증가, 디스크 탐색 증가, 접근 속도 ↓

─────────────────────────────────────────────────────────────
■ 테이블 제약조건 (FK 참조 무결성 옵션)
─────────────────────────────────────────────────────────────

삭제 시 (ON DELETE)
- CASCADE  : 부모 데이터 삭제 시 자식 데이터도 함께 삭제
- RESTRICT : 자식 테이블에서 참조 중이면 부모 데이터 삭제 불가
- SET NULL : 부모 데이터 삭제 시 자식 테이블의 FK 값을 NULL로 변경
             (FK 컬럼이 NULL 허용이어야 함)

수정 시 (ON UPDATE)
- CASCADE  : 부모 PK 수정 시 자식 FK도 함께 수정
- RESTRICT : 자식 테이블에서 참조 중이면 부모 PK 수정 불가
- SET NULL : 부모 PK 수정 시 자식 FK 값을 NULL로 변경

사용법
  CONSTRAINT 외래키명 FOREIGN KEY (컬럼명)
  REFERENCES 테이블명(컬럼명)
  ON DELETE CASCADE   -- 또는 RESTRICT / SET NULL
  ON UPDATE CASCADE   -- 또는 RESTRICT / SET NULL

─────────────────────────────────────────────────────────────
■ 인덱스 설계
─────────────────────────────────────────────────────────────

정의 : 데이터를 빠르게 찾기 위해 만드는 검색용 목차

인덱스 적용 기준
① 분포도가 10~15% 이내인 컬럼
   분포도 = (1 / 컬럼 값의 종류 수) × 100
   → 분포도가 낮을수록(고유값이 많을수록) 인덱스 효율이 높다

② 분포도가 기준 이상이더라도 부분 처리가 목적인 경우
   (예: 전체 데이터의 2%에 해당하는 '취소' 상태만 주로 조회할 때)

③ WHERE, JOIN 조건에 자주 사용되는 컬럼

④ PK와 UNIQUE 제약조건 → 자동으로 인덱스 생성

⑤ 수정이 빈번하지 않은 컬럼 (INSERT/UPDATE/DELETE 시 인덱스도 갱신되어 부담 증가)

인덱스 종류
- 단독 인덱스  : 분포도가 좋은 컬럼에 단독으로 생성
  CREATE INDEX idx_user ON users(email);

- 결합 인덱스 : 여러 컬럼을 조합하여 자주 같이 조회하는 경우 생성
               컬럼 순서가 중요하다 (선두 컬럼부터 매칭)
  CREATE INDEX idx_member_order ON orders(member_id, order_date);

인덱스 설계 주의사항
- 새 인덱스가 기존 액세스 경로에 영향을 줄 수 있다
- 인덱스가 너무 많으면 DML 성능 저하 (오버헤드 발생)
  → INSERT 시 모든 인덱스 구조에 키값 추가, Page Split 발생 가능
- 인덱스는 추가 저장 공간 필요
- 넓은 범위 조회 시 Full Table Scan이 오히려 빠를 수 있다
- 대규모 DB에서는 테이블과 인덱스를 물리적으로 분리하여 저장

─────────────────────────────────────────────────────────────
■ 뷰 (View)
─────────────────────────────────────────────────────────────

정의 : SELECT 결과를 테이블처럼 저장하는 가상 테이블
       실제 데이터를 저장하지 않고, 조회 시 내부적으로 SELECT문을 실행한다.

특징
- 보안성  : 민감한 컬럼을 제외하고 필요한 컬럼만 노출 가능
            (예: 급여 테이블에서 이름/직급만 공개하는 뷰 생성)
- 독립성  : 원본 테이블 구조가 변경되어도 뷰를 통해 접근하는 앱은 코드 수정 불필요
- 단순화  : 복잡한 SQL을 뷰로 만들어 단순하게 재사용 가능

뷰 속성
- REPLACE (CREATE OR REPLACE 뷰이름 AS ...)
  → 이미 존재하는 뷰를 새 내용으로 재생성

- FORCE (ORACLE 전용)
  → 참조 테이블이 없어도 뷰 생성 가능. 단, 사용 시 에러 발생

- NOFORCE (ORACLE 전용)
  → 참조 테이블이 존재할 때만 뷰 생성 허용

- WITH CHECK OPTION
  → 뷰의 조건을 만족하는 행만 INSERT/UPDATE 허용

- WITH READ ONLY
  → 조회 전용 뷰. INSERT/UPDATE/DELETE 불가

뷰 설계 시 주의사항
- 복잡한 뷰는 성능이 느려질 수 있다
- 뷰 내부의 조건 컬럼에 인덱스가 걸려 있는지 확인해야 한다

─────────────────────────────────────────────────────────────
■ 클러스터 (Cluster)
─────────────────────────────────────────────────────────────

정의 : 자주 같이 조회되는 데이터를 디스크의 가까운 위치에 모아 저장하여
       조회 속도를 높이는 물리적 저장 방법

인덱스 vs 클러스터
- 인덱스  : 특정 행의 위치를 빠르게 찾는 목차
- 클러스터 : 관련 데이터를 물리적으로 가까이 모아두어 범위 조회/반복 조인이 빠름

적용 기준
- 분포도가 넓을수록(고유값이 많을수록) 유리
- 여러 블록 이상의 대용량 테이블에 적용 (소형 테이블은 효과 미미)
- 대량의 범위를 자주 조회할 때
- 여러 테이블이 빈번히 JOIN될 때
- UNION, DISTINCT, ORDER BY, GROUP BY가 빈번한 컬럼
- 수정이 자주 발생하지 않는 컬럼 기준으로 설정

주의사항
- 검색은 빨라지지만 INSERT/UPDATE/DELETE는 느려질 수 있다

생성 방법 (Oracle)
  1. 클러스터 생성
     CREATE CLUSTER 클러스터이름(컬럼명 타입);

  2. 클러스터 인덱스 생성
     CREATE INDEX 인덱스명 ON CLUSTER 클러스터명;

  3. 클러스터를 사용하는 테이블 생성
     CREATE TABLE 테이블명(...) CLUSTER 클러스터이름(컬럼);

MySQL : PK를 기준으로 자동 클러스터형 인덱스 생성 (InnoDB 엔진)

─────────────────────────────────────────────────────────────
■ 파티션 (Partition)
─────────────────────────────────────────────────────────────

정의 : 하나의 큰 테이블을 내부적으로 여러 조각으로 나누어 저장하는 기술
       겉으로는 하나의 테이블로 보이지만 DBMS가 내부적으로 분리 관리

장점
- 파티션 프루닝(Partition Pruning) : 필요한 파티션만 읽어 검색 속도 향상
- 오래된 데이터를 파티션 단위로 빠르게 삭제/백업 가능
  (DELETE 쿼리 대신 ALTER TABLE ... DROP PARTITION 사용)
- 전체 데이터 훼손 가능성 감소
- 디스크 분산 저장으로 I/O 성능 향상

파티션 종류

① 범위 분할 (Range Partitioning)
   - 사람이 직접 값의 범위 기준으로 분할
   - 날짜/기간 기반 조회에 유리, 오래된 데이터 관리 편리
   - 데이터가 특정 파티션에 편중될 수 있음
   - 주로 사용 : 주문, 로그, 게시글, 이력 데이터
   CREATE TABLE 테이블명(...)
   PARTITION BY RANGE(컬럼)(
       PARTITION p2024 VALUES LESS THAN (2025),
       PARTITION p2025 VALUES LESS THAN (2026)
   );

② 해시 분할 (Hash Partitioning)
   - DB가 해시 계산으로 데이터를 자동 균등 배분
   - 계산식 : 해시값 % 파티션 개수 → 저장할 파티션 결정
   - 특정 파티션에 데이터 편중 방지
   - ID 기반 조회에 적합, 범위 조회에는 비효율적
   - 주로 사용 : 회원, 사용자, 고객, 게임 사용자 데이터
   CREATE TABLE users(...) PARTITION BY HASH(user_id) PARTITIONS 4;

③ 조합 분할 (Composite Partitioning)
   - 파티션 기준 2개 이상 조합 (1차 분할 후 내부에서 2차 분할)
   - 예: 1차 → 주문일 기준 범위 분할, 2차 → 고객번호 기준 해시 분할
   - 1차 파티션만으로 데이터가 너무 많을 때 사용
   CREATE TABLE orders(...)
   PARTITION BY RANGE(YEAR(order_date))
   SUBPARTITION BY HASH(customer_id) SUBPARTITIONS 4 (...);

파티셔닝 순서
1. 파티션 종류 결정 (범위/해시/조합)
2. 파티션 키 선정 (데이터를 나눌 기준 컬럼 결정)
3. 파티션 수 결정 (데이터 양, 조회 패턴, 보관 정책 고려)

─────────────────────────────────────────────────────────────
■ 테이블 스페이스 (Table Space)
─────────────────────────────────────────────────────────────

정의 : 테이블과 인덱스가 실제로 할당되는 물리적 저장 공간 단위
       성능 최적화를 위해 테이블용 테이블스페이스와
       인덱스용 테이블스페이스를 분리하여 구성하는 것이 권장된다.

─────────────────────────────────────────────────────────────
■ 시퀀스 (Sequence)
─────────────────────────────────────────────────────────────

정의 : 중복 없는 순차적 정수를 자동 생성하는 DB 객체
필요성 : 동시 접속자가 많은 시스템에서 기본키 중복 없이 안전하게 고유 번호를 발행하기 위해 사용

ORACLE 사용 예
  CREATE SEQUENCE member_seq START WITH 1 INCREMENT BY 1;
  INSERT INTO member VALUES (member_seq.NEXTVAL, ...);

MYSQL : AUTO_INCREMENT 사용

4. SQL 언어 분류
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DDL (Data Definition Language) : CREATE, ALTER, DROP
→ 데이터베이스 객체(테이블, 인덱스 등) 구조 정의

DML (Data Manipulation Language) : SELECT, INSERT, UPDATE, DELETE
→ 테이블 내부 데이터 조작

DCL (Data Control Language) : GRANT, REVOKE, ROLE
→ 사용자 권한 및 보안 관리

  GRANT 권한 ON 테이블 TO 유저명;
  REVOKE 권한 ON 객체명 FROM 사용자명;

  ROLE : 여러 권한을 하나의 그룹으로 묶어 관리
  CREATE ROLE 역할이름;
  GRANT SELECT, INSERT ON 테이블 TO 역할이름;
  GRANT 역할이름 TO 유저이름;

  DCL 주의사항
  - 최소 권한 원칙 준수 (꼭 필요한 권한만 부여)
  - ALL PRIVILEGES 남용 금지
  - 운영 환경에서는 권한 부여 이력 관리 필수

TCL (Transaction Control Language) : COMMIT, ROLLBACK, SAVEPOINT
→ 트랜잭션 제어, 데이터 무결성 유지, 오류 발생 시 복구 가능

5. SQL 처리 흐름
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

─────────────────────────────────────────────────────────────
■ 처리 단계 : 구문 분석 → 실행 → 추출
─────────────────────────────────────────────────────────────

[ 1단계 : 구문 분석 (Parsing) ]

공유 풀(Shared Pool)
- 이전에 실행된 SQL문과 실행 계획을 캐싱해두는 공유 메모리 영역

① 공유 풀 검색
   - 동일한 SQL이 존재하면 → Hard Parsing 생략, 바로 실행 단계로 이동
   - 존재하지 않으면 → 아래 구문 분석 3단계 수행

② 구문 분석 3단계
   1) 문법 검사  : SQL 문법이 올바른지 확인
   2) 의미 검사  : 참조 테이블/컬럼이 실제로 존재하는지 확인
   3) 권한 검사  : 해당 객체에 접근 권한이 있는지 확인

③ 옵티마이저(Optimizer)
   - 구문 분석 완료 후 가장 효율적인 실행 계획(Execution Plan) 수립
   - PLAN_TABLE에 실행 계획 저장

[ 2단계 : 실행 (Execute) ]

데이터베이스 버퍼 캐시(Buffer Cache)
- 디스크에서 읽어온 데이터를 임시 저장하는 메모리 공간

① 버퍼 캐시에 데이터가 있을 때
   → 메모리에서 즉시 읽음 (디스크 I/O 없음, 처리 속도 빠름)

② 버퍼 캐시에 데이터가 없을 때
   → 디스크의 데이터 파일(Data File)에서 직접 읽음 (느림)
   → 읽어온 데이터를 버퍼 캐시에 저장 (이후 재사용)

③ SELECT가 아닌 DML (INSERT/UPDATE/DELETE)
   → 버퍼 캐시 영역에서 변경 작업 수행
   → COMMIT 해야 변경사항이 디스크에 영구 반영됨

[ 3단계 : 추출 (Fetch) ]
- SELECT문에서만 실행되는 단계
- 실행 결과를 클라이언트(사용자)에게 반환

─────────────────────────────────────────────────────────────
■ SQL 작성 시 고려사항
─────────────────────────────────────────────────────────────

1. DBMS별 SQL 특성을 충분히 이해하고 작성
2. 옵티마이저의 실행 계획 수립 과정을 이해하고 작성
   - 인덱스를 사용할 수 있는 조건인가?
   - 어떤 테이블부터 읽는 것이 유리한가?
   - WHERE 조건이 너무 넓지 않은가?
   - 불필요한 정렬이 발생하지 않는가?
3. 실행 계획에 따라 수행 속도가 크게 달라질 수 있음
4. 옵티마이저가 비정상 동작 시 → 힌트, 인덱스 추가, JOIN 순서 변경 등으로 조정
5. 조건을 명확히, 필요한 컬럼만 조회, 인덱스를 활용하는 형태로 작성
6. 좋은 SQL은 결과를 미리 추론하고 집합적으로 접근하여 작성

─────────────────────────────────────────────────────────────
■ 힌트 (Hint)
─────────────────────────────────────────────────────────────

정의 : 개발자가 옵티마이저에게 SQL 실행 방법을 직접 지시하는 기능

문법 : /*+ 힌트내용 */

예시
  /*+ INDEX(EMP PK_EMP) */   → 특정 인덱스를 강제로 사용
  /*+ FULL(EMP) */           → 인덱스 대신 Full Table Scan 강제

─────────────────────────────────────────────────────────────
■ 바인드 변수 (Bind Variable)
─────────────────────────────────────────────────────────────

정의 : 조건절에 리터럴 값 대신 변수를 사용하는 방식
       WHERE phone = '01012345678'  →  WHERE phone = :b1

효과 : SQL이 최초 1회만 파싱되어 공유 풀에 저장되고 이후 재사용
       → CPU 자원 절약, 공유 풀 효율 극대화

6. 절차형 SQL (PL/SQL)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

정의 : 변수, 조건문, 반복문, 예외 처리 등을 포함하여 SQL을 절차적으로 작성하는 방식
       Oracle의 절차형 SQL 언어가 PL/SQL

─────────────────────────────────────────────────────────────
■ 기본 구조
─────────────────────────────────────────────────────────────

일반 블록
  DECLARE
      v_name VARCHAR2(50);   -- 변수 선언
  BEGIN
      -- 실행 코드
  EXCEPTION
      WHEN NO_DATA_FOUND THEN ...   -- 예외 처리
  END;
  /

조건문
  IF v_score >= 60 THEN
      DBMS_OUTPUT.PUT_LINE('합격');
  ELSE
      DBMS_OUTPUT.PUT_LINE('불합격');
  END IF;

반복문
  LOOP
      ...
      EXIT WHEN 조건;
  END LOOP;

─────────────────────────────────────────────────────────────
■ 저장 객체 종류
─────────────────────────────────────────────────────────────

① Stored Function (함수)
   - 반드시 값을 반환해야 함 (RETURN 필수)
   - 계산 결과나 특정 값 반환 목적
   CREATE OR REPLACE FUNCTION 함수명(매개변수)
   RETURN 반환타입
   IS
       지역변수
   BEGIN
       ...
       RETURN 반환값;
   END;

② Stored Procedure (프로시저)
   - 특정 작업 수행 목적 (반환값 필수 아님)
   - 데이터 입력/수정/삭제 등 작업에 주로 사용
   - 매개변수 종류
     IN    : 외부에서 값을 받아오는 매개변수
     OUT   : 외부로 값을 내보내는 매개변수
     INOUT : 받아서 처리 후 내보내는 매개변수

   CREATE OR REPLACE PROCEDURE 프로시저명(매개변수)
   IS
       지역변수
   BEGIN
       ...
   END;

   저장 프로시저의 성능 장점
   → 복잡한 로직을 DB 서버 내에 미리 저장해두므로
     단 한 번의 호출로 모든 작업을 DB 내부에서 처리
     → 매 연산마다 발생하던 네트워크 트래픽 감소, 성능 향상

③ Stored Package (패키지)
   - 관련 있는 프로시저/함수를 하나의 그룹으로 묶는 객체
   - 선언부 (PACKAGE) + 본문 (PACKAGE BODY)로 구성

   패키지 선언부
   CREATE OR REPLACE PACKAGE 패키지명 IS
       변수 선언;
       CURSOR 커서 선언;
       예외 선언;
       PROCEDURE 프로시저명(매개변수);
       FUNCTION 함수명(매개변수) RETURN 자료형;
   END;

   패키지 본문
   CREATE OR REPLACE PACKAGE BODY 패키지명 IS
       -- 선언부에서 정의한 프로시저/함수의 실제 구현
   END 패키지명;

   패키지 사용
   패키지명.프로시저명();
   패키지명.함수명;

④ Trigger (트리거)
   - INSERT/UPDATE/DELETE 이벤트 발생 시 자동으로 실행되는 프로시저
   - 트리거 내부에서 COMMIT/ROLLBACK 사용 불가
     → 트리거는 상위 트랜잭션의 일부로 동작하므로,
       내부에서 TCL을 사용하면 상위 트랜잭션의 원자성이 파괴됨

   CREATE OR REPLACE TRIGGER 트리거명
   [BEFORE|AFTER] [INSERT|UPDATE|DELETE] ON 테이블명
   [FOR EACH ROW]   -- 영향받은 행 수만큼 실행
   [WHEN 조건]
   DECLARE
       변수 선언
   BEGIN
       실행 코드  -- :NEW.컬럼명, :OLD.컬럼명 사용 가능
   END;

─────────────────────────────────────────────────────────────
■ 주요 PL/SQL 개념 용어
─────────────────────────────────────────────────────────────

- 파라미터 (Parameter)  : 프로시저에 값을 입력받거나 결과를 내보내기 위해 선언하는 매개변수
- 커서 (Cursor)         : 행 단위로 복수의 데이터를 순차적으로 참조/제어하는 포인터 역할
- 예외 (Exception)      : 실행 중 오류 처리 구문
- 사용자 정의 예외      : 시스템 에러가 아닌, 개발자가 직접 정의하는 비즈니스 규칙 위배 예외
- DBMS_OUTPUT          : 변수 값이나 메시지를 화면에 출력하는 Oracle 내장 패키지
                          PUT_LINE() 메서드 사용

7. SQL*Plus 명령어
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SQL*Plus : Oracle이 제공하는 명령어 기반 DB 접속/실행 프로그램
SQL 버퍼 : 가장 최근에 실행한 SQL문을 임시 저장하는 메모리 공간

[ 파일 명령어 ]
SAVE 파일명       : 버퍼의 SQL을 파일로 저장
GET 파일명        : 파일을 버퍼로 불러오기
SPOOL 파일명      : 이후 실행 결과를 파일에 저장 시작
SPOOL OFF         : 파일 저장 종료 (반드시 작성해야 함)

[ 편집 명령어 ]
L (LIST)          : 현재 SQL 버퍼 내용 확인
A (APPEND)        : 현재 줄 끝에 내용 추가
C (CHANGE)        : 문자열 변경   예) C/이전값/새값
I (INSERT)        : 현재 줄 다음에 새 줄 삽입 (마침표(.)로 종료)
DEL               : 현재 선택된 줄 삭제

[ 실행 명령어 ]
RUN               : 버퍼 내용 출력 후 실행
/                 : 버퍼 내용 바로 실행
START 파일명      : SQL 파일 실행
@ 파일명          : SQL 파일 실행 (START와 동일)

[ 환경 명령어 ]
SET SERVEROUTPUT ON   : DBMS_OUTPUT 결과를 화면에 표시 (PL/SQL 출력 전 필수)

[ 형식 명령어 ]
COLUMN 컬럼명 FORMAT A20   : 컬럼 출력 너비 지정

─────────────────────────────────────────────────────────────
■ 테스트 수행 절차
─────────────────────────────────────────────────────────────

1. 실행 전 데이터 확인 (SELECT로 현재 상태 조회)
2. 프로시저 실행
3. 실행 후 데이터 확인 (결과 비교)
4. 의도대로 동작하지 않으면 디버깅

테스트 체크리스트
- 실행이 되는가 (문법 오류 없이 실행 완료 여부)
- 출력이 맞는가 (예상한 값과 동일한지)
- 데이터가 바뀌었는가 (DML 후 COMMIT 확인)
- 오류가 없는가 (SHOW ERRORS 확인)
- 정상값/잘못된 값/NULL 등 다양한 케이스 테스트

─────────────────────────────────────────────────────────────
■ 테스트 주의사항
─────────────────────────────────────────────────────────────

운영 DB에서 직접 테스트 금지!
이유 : 잘못된 로직으로 실제 고객 데이터 오염,
       LOCK 충돌로 운영 서비스 중단 위험

방안 : 개발자 전용 테스트 DB 구축 + 운영 데이터를 복사한 더미 데이터 사용

─────────────────────────────────────────────────────────────
■ 무한 루프 발생 시 점검 사항
─────────────────────────────────────────────────────────────

반복문의 종료 조건이 올바르게 설계되었는지 확인
(EXIT WHEN 조건이 절대 true가 되지 않는 경우 → 무한 루프)

─────────────────────────────────────────────────────────────
■ Java ↔ DB 연동
─────────────────────────────────────────────────────────────

- JDBC    : Java와 DBMS를 연결해주는 드라이버 인터페이스
- Connection       : DB 연결 객체
- PreparedStatement : SQL을 미리 컴파일하여 실행 (SQL Injection 방지, 성능 향상)
  → 파라미터가 있는 SQL 실행 시 사용  예) "SELECT * FROM member WHERE id = ?"
- ResultSet        : SELECT 결과를 담는 객체 (행 단위로 순차 접근)
  → 사용 후 반드시 close() 호출 (미호출 시 메모리 누수 발생)
- 논리 삭제        : 실제 행을 DELETE하지 않고 is_deleted 등 상태 컬럼을 UPDATE로 변경
                     (복구 가능, 이력 보관)

■ 성능 분석 도구
─────────────────────────────────────────────────────────────

TKPROF
- SQL Trace 파일(.trc)을 사람이 읽기 좋게 변환하는 성능 분석 도구
- 실제 실행 후 사후 분석
- 분석 항목 : CPU 사용 시간, 디스크 I/O 횟수, 처리 건수(Rows), 실행 횟수

SQL Trace 활성화
  ALTER SESSION SET SQL_TRACE = TRUE;
  -- SQL 실행
  ALTER SESSION SET SQL_TRACE = FALSE;

EXPLAIN PLAN
- SQL을 실제 실행하지 않고 옵티마이저가 수립할 실행 계획을 사전 예측하는 도구
- 결과를 PLAN_TABLE에 저장
- 인덱스 사용 여부, 액세스 경로, 조인 순서 등 확인

TKPROF vs EXPLAIN PLAN 비교
  구분           TKPROF                    EXPLAIN PLAN
  실행 여부      실제 실행 후 분석 (사후)   실행 없이 예측 (사전)
  분석 내용      실제 CPU/I/O/처리건수      액세스 경로 및 실행 순서
  결과 위치      .trc 파일 → 변환 출력      PLAN_TABLE

APM (Application Performance Monitoring)
- 운영 중인 시스템의 성능을 모니터링하는 도구
- 가용성 : 사용자가 필요할 때 시스템을 정상 사용할 수 있는 정도
- 다운타임 : 장애/점검으로 서비스를 제공하지 못하는 시간

리소스 모니터링 vs E2E(엔드투엔드) 모니터링
- 리소스 모니터링 : CPU/메모리 등 서버 하드웨어 자원만 감시
                    → 서버 지표가 정상이어도 장애 원인 못 찾을 수 있음
- E2E 모니터링    : 사용자 요청 → DB 조회 → 외부 API 호출까지
                    전 트랜잭션 과정을 추적하여 병목 구간 파악 가능

─────────────────────────────────────────────────────────────
■ 성능 개선 절차 (6단계)
─────────────────────────────────────────────────────────────

1. 속도를 저하시키는 SQL 구문 재작성
   (WHERE 절 최적화, 서브쿼리 정리, IN → EXISTS 변경 등)

2. 실행 계획 개선
   (옵티마이저 힌트 적용, Driving 테이블 변경)
   ※ Driving 테이블 : 조인 시 가장 먼저 읽는 테이블

3. 인덱스 재구성
   (새 인덱스 추가 또는 기존 인덱스 조정)

4. 시스템 리소스 병목 구간 조정
   (Shared Memory, CPU, I/O 등 인프라 설정 최적화 → 시스템 관리자 협조)

5. 개선 후 동일한 테스트로 효과 검증
   (개선 전후 수치 비교)

6. 성능 개선 결과 문서화 및 공유
   (개선 전후 비교, 변경 내역, 테스트 결과 정리)

─────────────────────────────────────────────────────────────
■ 성능 측정 프로세스
─────────────────────────────────────────────────────────────

① 기준 요구사항 식별
   - 응답 시간, 처리 건수, 리소스 사용량 등 정량적 목표 정의

② 성능 측정 도구 설정
   - TKPROF 등 설정, Trace 로그 수집 준비

③ 프로시저 실행 및 측정 데이터 수집
   - 테스트용 데이터로 프로시저 실행, Trace 로그 수집

④ 결과 분석 및 성능 평가
   - 수행 시간, 블록 읽기 수, CPU 사용량, APM 지표 검토

⑤ 테스트 시나리오 설계 (실데이터 기반)
   - 정상 처리, 예외 상황, 대량 처리, 동시성, 복합 조건 등 다양한 케이스

⑥ 병목 지점 식별
   - 인덱스 미사용, Full Scan, 비효율적 조인 방식 점검

⑦ 성능 저하 원인 문서화
   - 병목 SQL과 원인 정리, 개선 항목 도출
