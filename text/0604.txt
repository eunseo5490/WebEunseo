데이터 조작 프로시저 최적화

SQL 처리 흐름
구문분석
- SQL문이 사용된 적이 있는지 없는지 판단(공유 풀 영역을 검색하여 판단)
※공유 풀 영역
- 데이터베이스 메모리 안에 있는 공간
- 이전에 실행된 SQL문과 실행 계획이 저장될 수 있다.

실행이 된 적이 있음 -> 구문분석 할 필요 없음
실행 된 적 없음 -> 구문분석 작업 수행

구분 분석이란?
- 사용자가 작성한 SQL문장을 DBMS가 이해할 수 있는 형태로 해석하는 과정
SELECT * FROM EMP WHERE EMPNO = 7369;
DBMS는 이 문자열을 보고
SELECT문인지
문법이 올바른지
EMP 테이블이 존재하는지
EMPNO 컬럼이 존재하는지
사용자가 권한이 있는지
같은 내용을 확인해야 한다.

구문 분석의 3단계
1. 문법 검사 : SQL문법이 맞는지 확인
2. 의미 검사 : 문법은 맞지만 실제 객체가 존재하는지 확인
3. 권한 검사 : 사용자가 해당 객체에 접근 가능한지 확인


실행단계
- 구문 분석이 끝난 SQL을 실제로 실행하는 단계
- 구문 분석 단계에서 실행 계획이 만들어졌다면, 데이터베이스는 그 계획에 따라 실제 데이터를 찾거나 변경을한다.

※실행 계획
- 어떤방법으로 SQL을 실행하는게 가장 빠를까? 를 계산
- 옵티마이저 : 계산하고 실행하는 역할, 옵티마이저가 선택한 실행 방법이 실행 계획이다.

- 구문 분석이 정상적으로 끝나면 서버 스포세스는 메모리 영역의 데이터베이스 버퍼 캐시를 검사

※ 데이터베이스 버퍼 캐시
- 디스크에서 읽어온 데이터를 잠시 저장해두는 메모리 공간
- 디스크는 데이터를 영구적으로 저장하지만 속도가 느리기 때문에
- 메모리에 잠깐 저장해놓는다.

데이터베이스 버퍼캐시에 존재 -> 꺼내서 사용

없음 -> 데이터 파일에서 읽고 -> 버퍼캐시에 저장

SELECT가 아닌 DML이라면 버퍼 캐시 영역에서 수정, 삭제, 추가를 한다.
※ COMMIT을 해야 변경사항이 확정된다.

추출단계
- SELECT문 에서만 실행 되는 단계
- 실행 결과를 사용자(클라이언트)에게 보내주는 단계

SQL 작성 시 고려사항
1. SQL의 특성을 충분히 이해 해야 한다.(DBMS별 작성 방법)
2. 옵티마이저가 실행 계획을 수립한 후 실행된다는 것을 이해해야 한다.
- 이 조건은 인덱스를 사용할 수 있는가?
- 이 조인은 어떤 테이블부터 읽는 것이 좋은가?
- WHERE의 조건이 너무 넓지는 않은가?
- 정렬이 불필요하게 발생하지는 않는가?
3. 실행 계획에 따라 수행 속도 차이가 크게 발생할 수 있다는것을 이해해야 한다.
4. 옵티마이저가 비정상적으로 동작한다면, 이를 추적하여 개발자가 원하는 실행 계획으로 동작될 수 있도록 조정하는 과정이 필요하다.
- 인덱스 추가
- SQL의 조건을 변경
- JOIN의 순서를 개선
- 힌트

※힌트란?
- 옵티마이저에게 SQL을 어떻게 실행할지 개발자가 직접 지시하는 기능

힌트 문법
/*+ */

인덱시를 사용하도록 지시
/*+ INDEX(EMP PK_EMP) */

FULL 힌트
/*+ FULL(EMP) */

5. 옵티마이저가 정상적인 실행 계획을 수립할 수 있도록 종합적이고 전략적인 포인트를 SQL에 부여하여 작성해야 한다.
- 조건을 명확하게 작성해야 한다.
- 불필요한 전체 조회를 줄인다.
- 인덱스를 사용할 수 있는 형태로 작성한다.
- 조인 조건을 정확히 작성한다
- 필요한 컬럼만 조회한다.

6. 좋은 SQL은 결과를 추론하고 집합적으로 접근해야 한다.
- 내가 최종적으로 필요한 데이터는 무엇인가?
- 몇 건 정도 조회될 것인가?
- 어떤 조건으로 데이터를 줄일 수 있는가?
- 조인이 필요한가?
- 정렬이 꼭 필요한가?
- 중복 제거가 필요한가?

SQL 성능 최적화를 위한 유틸리티 활용
TKPROF
- 실행되는 SQL문장에 대해 분석 정보를 제공하여 사용자가 특정 SQL문장을 어떻게 사용해야 할 것인지에 대한 가이드라인을 제공하는 도구

EXPLAIN PLAN
- 사용자들이 SQL문의 액세스 경로를 확인하여 성능 개선을 할 수 있도록 SQL문을 분석하고 해석하여 실행계획을 수립하고, 관련 테이블에 저장하도록 지원해주는 도구
---------------------
데이터 조작 프로시저 성능 개선하기
업무 분석가에 의해 정의된 요구사항을 기준으로, 성능 측정 도구를 활용하여 데이터 조작 프로시저의 성능을 측정한다.

1. 성능 측정을 위한 기준 요구사항 식별
- 응답 시간, 처리 건수, 리소스 사용량 등 정량적 성능 목표를 분석하고, 테스트 대상 프로시저별 성능 기준 정의하기

2. 성능 측정 도구 설정
- 성능 도구(TKPROF 등)를 설정하고 Trace 로그 수집을 준비한다.
※Trace 파일
- Oracle이 SQL 실행 과정을 기록한 로그 파일이다.
언제 실행했는지
몇 번 실행했는지
몇 개의 블록을 읽었는지
몇 개의 행을 조회했는지
CPU를 얼마나 사용했는지
디스크를 얼마나 읽었는지

ALTER SESSION SET SQL_TRACE = TRUE;
이후에 SQL들을 실행
ALTER SESSION SET SQL_TRACE = FALSE;

3. 대상 프로시저를 실행하고 측정 데이터를 수집한다.
- 테스트용 데이터를 사용하여 프로시저를 실행하고, 실행 결과 및 Trace 로그를 수집한다.

4. 측정 결과를 분석하여 실행 성능을 평가한다.
- 수행 시간, 블록 읽기 수, CPU 사용량 등을 바탕으로 성능을 분석하고, TKPROF 결과 또는 APM 지표를 검토한다.

※APM(Application Performance Monitoring)
- 운영중인 시스템에 대한 가용성 확보, 다운타임 최소화 등을 통해 안정적인 시스템 운영을 위하여 부하량과 접속자 파악 등 장애 진단을 목적으로 사용하는 성능 모니터링 도구

실 데이터를 기반으로 테스트를 수행하여 데이터 조작 프로시저의 성능에 영향을 주는 병목 구간을 파악한다.

1. 실데이터를 반영한 테스트 환경을 구성한다.
- 운영 데이터의 복사본 또는 유사 데이터를 준비하여 성능 테스트 환경을 구성한다.

2. 테스트 시나리오를 설계한다.
- 대량 처리, 복합 조건, 동시성 등 다양한 상황을 반영하여 테스트 시나리오를 작성한다.

주문 처리 프로시저
CALL proccess_order(회원번호, 상품번호, 주문수량);
- 회원 존재 여부 확인
- 상품 재고 확인
- 주문 데이터 insert
- 상품 재고 update
- 결제 데이터 insert
- 처리결과를 반환

테스트 시나리오
- 정상 주문이 들어왔을 때 정상 처리 되는가?
- 재고가 부족하면 주문이 실패하는가?
- 주문이 1건이 아니라 10만건이면 성능이 괜찮은가?
- 여러 사용자가 동시에  주문하면 재고가 꼬이지는 않는가?
- 복합 조건 검색이 느려지지 않는가?

3. 테스트를 수행하고 성능 로그를 수집한다.
- PL/SQL 블록 실행 또는 SQL Script 반복 실행을 통해 성능 데이터를 수집한다.

4. 병목 지점을 식별
- 실행 계획을 분석하여 인덱스 미사용, Full Scan, 테이블 조인 방식 등을 점검하고, 통계 정보 최신화 여부를 확인한다.

5. 성능 저하 원인을 문서화한다.
- 병목이 발생한 SQL과 원인을 정리하고, 개선 필요 항목을 도출하여 분석 보고서를 작성한다.

테스트 결과와 정의된 요구사항을 기준으로 데이터 조작 프로시저의 성능에 따른 이슈를 해결한다.

1. 속도를 저하시키는 SQL 구문을 재작성하여 성능을 개선한다.
- WHERE 절 최적화, 서브쿼리 정리, IN 대신 EXISTS 사용 등을 통해 쿼리 성능을 향상한다.

2. 실행 계획 개선
- 옵티마이저 힌트를 적용하거나, Driving 테이블을 변경하여 최적의 실행 경로를 유도한다.

※ Driving 테이블
- 조인을 수행할 때 가장 먼저 읽는 테이블(from에 적은거)

3. 인덱스를 재구성한다.
- 새로운 인덱스를 추가하거나 기존 인덱스를 조정하여 접근 효율성을 높인다.

4. 시스템 리소스 병목 구간을 조정한다.
- Shared Memory, CPU, I/O등 인프라 병목 구간이 원인일 경우 시스템 관리자의 협조를 통해 시스템 설정을 최적화 한다.

5. 개선 후 동일한 테스트로 효과를 검증한다.
- 동일한 테스트를 반복 실행하여 개선 전후 성능 차이를 수치로 비교하고 효과를 검증한다.

6. 성능 개선 결과를 문서화하고 공유한다.
- 개선 전후 비교, 변경 내역, 테스트 결과를 정리하여 성능 개선 보고서를 작성한다.
